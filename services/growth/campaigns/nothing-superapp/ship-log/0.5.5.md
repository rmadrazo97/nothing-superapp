# 0.5.5 — Prod DB drift emergency fix + idempotency rollout + security-advisor cleanup

**Shipped:** 2026-08-11
**Live at:** https://nothing-superapp.vercel.app

The safety-net wave. What started as "extend idempotency to 7 more tools" turned into a full prod-DB audit + repair after discovering that **five** committed migrations had never been applied to prod. Whole features that shipped in v0.5.2 and v0.5.3 have been silently 500'ing this whole time. Fixed all five, shipped the tooling that ensures the drift can never recur, and cleared the Supabase Security Advisor findings while we were in the schema anyway.

## How the drift was found

Mid-v0.5.4 release, Playwright hit a `toHaveValue('')` on the Settings email field. First hypothesis: race between navigation and the `/api/profile` fetch. Widened the timeout, still failed. Direct REST query against prod showed `column profiles.timezone does not exist` — migration 024 committed, never applied. Applied it, CI turned green, shipped v0.5.4.

Then W3 (the parallel worker building the migration-applied CI safety check for v0.5.5) ran their new script and reported: **three more migrations** were also drift — 020 (`mini_app_settings`), 021 (`body_metrics`), 023 (`food_search_ranking` + `is_canonical` + `rank_penalty` + 429 rows updated). All silently broken since v0.5.2/v0.5.3 shipped.

Applied all five (idempotent `if not exists`, ~15 seconds of psql each). Verified every previously-broken flow works against real prod.

## What was actually broken (in prod, for real users)

- **Body composition tracker (Gym MEASUREMENTS tab)** — v0.5.2 headline feature. Every save 500'd because the `body_metrics` table didn't exist. Users who tried to log weekly measurements got a silent failure.
- **In-sub-app settings** — every write to `useMiniAppSettings()` 500'd because the `mini_app_settings` table didn't exist. Reminders info-banner dismissed state, Gym unit prefs, Fitness Pal ⚙ sheet — none of it persisted.
- **Food search ranking** — v0.5.3 claimed a canonical-first ranking with 251-entry curated seed + demotion of babyfood/frozen-unprepared noise. In prod, the SQL was still doing raw USDA sort (no `rank_penalty`, no `is_canonical`, no 429-row update). "Sweet potato" still led with babyfood.
- **Timezone setting** — Settings page email + name showed empty for every logged-in user for ~4 hours (v0.5.3 tag → v0.5.4 tag). The `/api/profile` GET was silently 500'ing. Client swallowed.
- **Copilot tool idempotency** — the v0.5.3 helper had nowhere to store its key. The 30-second-bucket dedupe was a no-op. Every "double reminder" bug the release notes claimed to fix was still active.

## What shipped in v0.5.5

### The safety net
- **`scripts/verify-migrations-applied.mjs`** — introspects every SQL file under `supabase/migrations/`, extracts expected DDL objects (tables, columns, indexes, unique indexes; the `if not exists` guards are the identifier source), queries prod via psql against `pg_class` + `information_schema.columns` + `pg_indexes`. Prints `[OK]` / `[MISS]` per object. Exits 1 if any missing. Cleanly skips (`[SKIP]`, exit 0) when prod creds absent — PR builds don't fail.
- **CI job `verify-migrations-applied`** in `.github/workflows/ci.yml`. `needs: typecheck-build`, `if: github.ref == 'refs/heads/main' && github.event_name == 'push'`. Any migration committed but not applied fails the release step immediately after merge. Would have caught the timezone incident in the same PR.
- **README §5** — documents the script + the GH secrets it needs (`SUPABASE_PROJECT_ID`, `SUPABASE_DB_PASSWORD`).

### Assistant hardening
- **Idempotency extended to 7 more write tools:** `log_weight`, `create_gym_routine`, `create_meal_plan`, `log_meal_from_plan`, `start_pomodoro`, `toggle_reminder`, `trigger_reminder_now`. Same pattern as `create_reminder`/`log_calorie_entry` — compute `sha256(tool + input + user + floor(ts/30s))`, check `copilot_tool_calls` for a prior hit within the 30s bucket, return cached output on hit. Task #108 → closed.

### Settings page — no more silent 500s
- `apps/web/src/app/app/settings/page.tsx` — replaced the boolean `profileLoaded` with a discriminated `ProfileLoadState = 'loading' | 'ready' | 'error'`. On error, the Profile section renders an inline card (label kicker `PROFILE · LOAD FAILED`, one-line body with the actual error message, RELOAD button that re-invokes the extracted `loadProfile` callback). Task #111 → closed.

### Migration 026 — Supabase Security Advisor cleanup
Ran Splinter security lints via Management API `POST /v1/projects/{ref}/database/query` (this CLI version doesn't ship `supabase inspect advisor`). Two safe findings addressed:
- **`set_updated_at()` trigger function** — pinned `search_path = public, pg_temp`. Trigger functions with mutable search_paths are classic privilege-escalation vectors.
- **`push_broadcasts` + `push_deliveries`** — had RLS enabled with 0 policies (which is correct: service-role writes only). Added explicit restrictive `no_direct_access` policies for `anon` + `authenticated` roles so intent is legible in-schema. Silences the `rls_enabled_no_policy` INFO.

One security finding deferred to v0.5.6: **move `pg_trgm` extension from `public` to `extensions` schema.** Requires DROP + CREATE on the trigram GIN indexes on `foods` (see migrations 018 + 023). Too risky to bundle with an emergency-fix release; will own its own dedicated migration + rollback plan.

## Lessons

### 1. "Committed" is not "deployed" — the `if not exists` invisibility trap

Every migration in this project uses `create table if not exists` + `alter table add column if not exists` + `create index if not exists`. That's the standard idempotency guard for re-runs. Its dark side: it makes **zero-runs invisible in every downstream test path**. Local dev has run every migration at least once, so tests pass. Unit tests mock the DB, so they pass. CI's typecheck + build doesn't touch a real DB, so it passes. The ONLY path where a never-applied migration surfaces is the client hitting `/api/*` in prod — and if the client has an over-broad `catch` swallowing to an empty state (as our Settings page did), even that surface stays quiet.

**Memoed:** treat migration application as a mandatory post-merge step, not a "the migration file is committed, we're done" step. `verify-migrations-applied.mjs` now enforces this at CI time. Worker briefs that touch `supabase/migrations/` must include the apply step explicitly.

### 2. Silent client-side catches are compound-interest bugs

The v0.5.3 `/api/profile` 500 hid for 4 hours because `settings/page.tsx` line 227 was `catch { if (!cancelled) setProfileLoaded(true); }`. No Sentry alert (client swallowed), no user complaint (empty form looks like "not filled in yet"), no dashboard signal (backend 500 count was low, drowning in noise). The bug compounded because a second downstream feature (idempotency guard, whose backing table 025 was also drift) also depended on a broken DB path — but nobody looked because the surface behaviour of an unfilled dedupe cache is "duplicate reminders" which we'd already "fixed."

**Memoed:** every `catch { setLoaded(true) }` is a candidate `catch { setState({error: msg}) }`. Loading and error are different states. Combined into one, they hide bugs indefinitely.

### 3. When you find one drift, look for more

The natural instinct after finding migration 024 wasn't applied was "apply it and move on." The correct instinct — enforced by W3's brief happening to run the script against the full tree — was "there might be more." There were four more. **Memoed:** any prod incident that fits a class ("committed but not applied", "missing env var", "stale cache") warrants a full-inventory scan of every candidate in that class before declaring the incident closed.

### 4. Security-advisor scans are cheap and worth doing at every release

Ran the Splinter lints in ~90 seconds via the Management API. Found 3 real findings (2 fixable now, 1 deferred). If they had been running at every push, they would have been caught in the migration that introduced each. Cost: near-zero. Coverage: the whole schema every time. **Memoed:** add a "supabase security advisor scan" section to the release-broadcaster GH Action so every release fires the lints + posts the results as a PR/commit comment. Even better: fail the CI if a NEW WARN or ERROR-level finding appears.
