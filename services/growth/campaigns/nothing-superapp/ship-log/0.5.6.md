## What shipped

### Migration 027 — pg_trgm to extensions
Splinter's `extension_in_public` was the last unclear WARN after v0.5.5's cleanup. Move via `ALTER EXTENSION pg_trgm SET SCHEMA extensions`. The critical property that made it zero-downtime: operator class OIDs (`gin_trgm_ops`) are stable across the move, so the GIN indexes on `foods` (mig 014) + `food_aliases` (mig 018) stayed valid. No drop/recreate against ~8k rows.

Supabase-managed roles already have `search_path = "$user", public, extensions`, so unqualified references to `similarity()`, `%`, `word_similarity()` continue to resolve in every RPC and SQL string in the codebase. Verified: `select nspname ... where extname='pg_trgm'` returns `extensions`; both GIN indexes still present in `pg_indexes`; smoke query `select name from foods where lower(name) % 'sweet potato' order by similarity(...) desc limit 5` returns the expected 5 rows.

Rollback is a single line (`ALTER EXTENSION pg_trgm SET SCHEMA public`) — captured in the migration file's footer.

### Automated Splinter scan
`scripts/security-advisor-scan.mjs` — ESM Node script that runs 6 well-known Splinter security queries against prod via `POST https://api.supabase.com/v1/projects/{ref}/database/query`:

1. `rls_disabled_in_public` — public tables without RLS. **ERROR** if hit.
2. `rls_enabled_no_policy` — RLS enabled with zero policies. **INFO** if hit.
3. `security_definer_view` — views without `security_invoker=on`. **WARN** if hit.
4. `function_search_path_mutable` — app-owned functions without pinned search_path. **WARN** if hit.
5. `extension_in_public` — extensions in `public` schema. **WARN** if hit.
6. `auth_users_exposed` — views/tables that leak `auth.users` columns. **ERROR** if hit.

Exits 0 for OK/INFO only, 1 for WARN+/ERROR. `--json` flag for CI parsing. Cleanly skips if `SUPABASE_MANAGEMENT_TOKEN` absent.

CI wiring at `.github/workflows/security-advisor.yml` — runs on push to main + daily 06:00 UTC cron. Posts findings as a commit comment via `gh api ... /comments` on failure.

**Local run right now: all 6 green.** (First time in project history, thanks to the migration 026 + 027 pass.)

### CI verify-migrations fallback
The v0.5.5 CI job for `verify-migrations-applied` failed on prod itself — not because of drift but because `SUPABASE_PROJECT_ID` GH secret is empty/wrong. Ironic (the safety net failing on the same class of misconfig it's supposed to catch), and easy to fix: added a fallback that derives the project ref from `SUPABASE_URL` (which is set at workflow-env level as `NEXT_PUBLIC_SUPABASE_URL`, unmasked because it's public).

### Canonical foods backfill
Post-migration-023 audit revealed 0 rows with `is_canonical=true` in prod — the `rank-foods.mjs` backfill script from v0.5.3 had never been run against prod. Ran it now: 60 canonical rows flagged, 165 patterns skipped (no matching USDA row). The 165-skip rate means our `canonical-foods.json` patterns are largely mis-aligned with USDA SR Legacy's actual naming ("Chicken breast, roasted, skin removed" vs pattern `"chicken breast, roasted, skinless"` etc). Pattern audit queued for v0.5.7 (#115).

Notably: this is a THIRD class of drift not covered by the `verify-migrations-applied` CI check — "the migration ran but the associated one-time script never did." Adding a `verify-backfills-run.mjs` sibling script is on the roadmap.

## Lessons

### 1. The "run this script once" step is invisible drift

Migration 023 was applied. `verify-migrations-applied.mjs` now catches "SQL committed but not applied." But it can't catch "SQL applied and an accompanying script never ran." The 165-skip / 0-canonical-rows state was invisible to every schema check because `is_canonical` is a column that CAN be all-false and still be valid.

**Memoed:** any migration that says "and then run scripts/backfill-X.mjs" needs to be paired with a check that the backfill actually ran. Idea: have every backfill script write a row into a `backfill_log` table on success. `verify-backfills-run.mjs` compares `supabase/migrations/*.sql` + a co-located `backfill/*.mjs` naming convention against `backfill_log` rows in prod.

### 2. Safety nets that fail their own protection are worse than none

`verify-migrations-applied` failed on the v0.5.5 CI run because a GH secret it needed was empty. If someone had glanced at the pipeline and seen it red, they'd assume "the same class of drift the v0.5.5 release fixed is happening again" and start diagnosing false positives. **Memoed:** safety-net jobs must be extra-robust against configuration issues. Every optional secret should have a fallback derivation path (like `SUPABASE_URL` → project ref). Every skip path should log a clear `[SKIP]` so red-ness always means "found a real problem," not "misconfigured myself."

### 3. Every "we should run this regularly" promise is a candidate cron

The Splinter scan was on the followup list from v0.5.5. In the natural course of a busy day, that scan would have run "sometimes" and drifted to "never." Wiring it into the daily cron makes the promise durable. **Memoed:** any "we should periodically ..." promise should either be a cron by end-of-week or explicitly downgraded to "manual, don't rely on it."

### 4. Silent-catch is not one bug per site — it's ONE bug repeated everywhere

The v0.5.5 Settings fix was a single-page fix. W6's sweep proved the same pattern was present in the entire mini-app catalog. Fixing 5 more today; another N remain in categories W6 flagged as INTENTIONAL that may need a second look. **Memoed:** whenever a bug shape matches "swallowed catch," start the audit before you finish the immediate fix. Fix the class, not the instance.
