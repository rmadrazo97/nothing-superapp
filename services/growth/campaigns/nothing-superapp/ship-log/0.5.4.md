# 0.5.4 — Generative UI: the assistant renders instruments, not paragraphs

**Shipped:** 2026-08-10
**Live at:** https://nothing-superapp.vercel.app

The direction wave. Two hours after v0.5.3 tagged, Phase 2 of the same day's parallel run landed and unlocked the biggest visual change since the shell itself: the copilot no longer answers quantitative questions with markdown tables. It calls `render_*` tools that emit typed payloads, and the client hydrates them into an 8-component pixel-panel library sharing one signature element.

## The headliner

Ask the copilot "how many kcal left today" and instead of `You have 320 kcal remaining out of 2200 for today...` you get a `<PixelProgressDots>` panel with a segmented progress bar and hero numeral. Ask "show my weight trend" and you get a `<PixelLineChart>` with plotted-dot points over a pixel-grid backdrop. Ask "compare last 4 weeks by muscle group" and you get a **grouped** `<PixelBarChart>` with PUSH · PULL · LEGS at W1 W2 W3 W4.

The signature element that ties the family into one instrument suite: a **2×2 cadmium LED cluster in the top-right of every `<PixelCard>`**. It reads as "power-on indicator" — every panel is an instrument, not a card. That single 8-pixel decoration is the difference between "cool components" and "coherent visual language."

## How it was built

- **Wave A + B (earlier today, v0.5.2)** — 6 workers shipped shell primitives (SwipeableRow, UndoSnackbar, BottomSheet, MiniAppSettingsPanel), body-composition tracker, D3's first PLAN redesign, gym unit settings.
- **Wave Y (this morning, v0.5.3)** — 3 workers shipped assistant race fix + timezone + idempotency + PLAN v2 + Fitness Pal chrome + food-search ranking + FROM PLAN + reminders rename + gym tap-to-START + `<PixelLoader>` (the seed).
- **Phase 2 (this afternoon, v0.5.4)** — 1 worker in the assistant zone. Built the pixel-panel component library first (design plan → 8 components), then the 7 render_* tools, then wired the render pipeline. One commit, one push.
- **Wave Z (this release)** — bump + push + broadcast pattern from v0.5.3, second time around.

Total elapsed from morning to v0.5.4 tag: ~7 hours.

## What shipped

### Pixel-panel component library
Located at `apps/web/src/components/pixel-ui/`. Shared atoms across all 8 components:
- **3px cell + 1px gap** grid (same as `<PixelLoader>` `md` size).
- **Doto for numerals**, Space Mono for labels, Inter for body — inherits the locked design tokens.
- **Cadmium ember-red accent** on active/positive/current elements; muted graphite for backdrop.
- **2×2 cadmium LED cluster** top-right of every `<PixelCard>` — the signature.

Components:
- `<PixelCard>` — the chassis. Hairline border, near-black canvas, LED cluster, label kicker + hero slot.
- `<PixelTicker>` — big numeric readout with delta chip. Use: WEIGHT · 78.4 kg · ▼ 0.3.
- `<PixelBarChart>` — vertical bars from stacked 3px cells. Supports single series + grouped for W1 W2 W3 W4 × PUSH · PULL · LEGS.
- `<PixelLineChart>` — plotted-dot line over hairline pixel-grid backdrop. Use: WEIGHT TREND · LAST 4 WEEKS.
- `<PixelProgressDots>` — segmented dot bar. Use: KCAL LEFT · TODAY · 22/30 OF 2200.
- `<PixelArc>` — half-arc gauge with hero numeral in the well. Use: POMODORO · CYCLE 3/4 · 18 MIN.
- `<PixelDataTable>` — mono grid, per-column alignment, hairline rows. Use: OPTIONS · LUNCH by kcal/P/C/F.
- `<PixelMetricGrid>` — 2×2 tile of tickers. Use: KCAL · PROTEIN · CARBS · FAT weekly rollup.

Schema shape at `apps/web/src/components/pixel-ui/schemas.ts`. Barrel export via `index.ts`.

### Assistant `render_*` tools
7 zero-side-effect tools at `apps/web/src/lib/ai/tools/render-*.ts`:
- `render_stat_ticker` — one big number + delta.
- `render_bar_chart` — vertical bars (single or grouped).
- `render_line_chart` — sparkline / trend.
- `render_progress_dots` — progress toward goal.
- `render_arc_graph` — cycle / gauge.
- `render_data_table` — tabular options with sortable columns.
- `render_metric_grid` — 2×2 tile of KPIs.

Every tool returns `{version: 1, kind: '<name>', data: <input-shape>}`. Version bump prepared for the day we redesign a component and need old chats to still render (they'll fall through to a legacy switch case).

### Copilot route system prompt
`apps/web/src/app/api/copilot/route.ts` gained a "Generative UI" block with explicit routing rules:
- Quantitative + single number → `render_stat_ticker`
- Quantitative + trend over time → `render_line_chart`
- Quantitative + comparison across categories → `render_bar_chart` (single) or `render_bar_chart` grouped
- Progress toward a numeric goal → `render_progress_dots`
- Circular / cyclical state → `render_arc_graph`
- Options with multiple attributes to compare → `render_data_table`
- Multi-KPI rollup → `render_metric_grid`

Prose-first for narrative answers; render-first for anything with numbers.

### Client-side render pipeline
`apps/web/src/components/copilot/CopilotChat.tsx` — `renderPixelPayload()` switch dispatches on `part.output.kind`. Wired into the tool-part render loop between the SSE parser and the message layout. `<ToolCallCard>` fallback preserved for `input-*` state (tool arguments streaming in) and for tools with side effects like `create_reminder` (the confirmation card is more valuable there than a chart would be).

### Design proof-sheet
`/dev/pixel-ui` renders every render_* payload against representative sample data on one page. Design plan at `services/growth/campaigns/nothing-superapp/design/pixel-ui-v0.5.4.md`. 3 verification screenshots at `services/growth/campaigns/nothing-superapp/design/screenshots/pixel-ui/`. Not gated behind auth (harmless — no reads, no writes; only sample data).

## Lessons

### 1. The loading state IS the design language of the answer

When `<PixelLoader>` shipped in v0.5.3 as a "cool spinner replacement," it accidentally seeded the entire v0.5.4 direction. The pixel-dot idiom — 3px cell + 1px gap + cadmium accent — read as instrument-panel aesthetic. Once it was there for THINKING / LOADING CHAT / tool-in-progress, extending it to the answer itself was the only coherent move: you can't have a beautiful pixel-dot loader hydrate into a boring markdown table. The loader forced the render library. Memoed: when a loading state develops a strong visual identity, the answer surface has to match — otherwise the identity reads as a bug.

### 2. Signature element > component polish

A generative UI component library with 8 well-designed components looks like Shadcn. A generative UI component library with 8 well-designed components + ONE signature element (2×2 LED cluster top-right of every card) reads as "instrument suite." That single decoration — 8 pixels total — is the difference between "Claude UI" and "Nothing OS UI." Memoed: before shipping any component family, name the ONE decoration that appears in every member. If you can't, the family isn't a family yet.

### 3. Zero-side-effect tools scale differently

The 7 `render_*` tools were written in one session because they share the exact same shape: typed input schema, `{version, kind, data}` return, no writes, no idempotency, no audit-log entry, no auth beyond the outer request. That uniformity is only possible BECAUSE they don't mutate anything. Write tools (`create_reminder`, `log_calorie_entry`) each need bespoke plumbing (idempotency, RLS check, downstream trigger). Read/render tools can be templated. Memoed: for assistant tool sprawl, separate the "render" surface from the "act" surface early — they scale on different curves.

### 4. Payload versioning at line 0 costs nothing

Every render_* tool wraps its output in `{version: 1, kind: '<name>', data: <shape>}`. Deciding to do this took ~10 seconds of thought and adds one field. NOT doing it would cost a full-fleet migration the first time a component gets redesigned (v0.6.x will redesign `<PixelBarChart>` when grouped-with-error-bars ships) — every persisted chat message with the old shape would have to be either backfilled or fall through to a broken renderer. Memoed: any persisted payload shape gets a version field on day 1, unconditionally. The one-time 10-second decision buys arbitrary future migrations.

### 5. Two-phase parallel worker pattern held for a fourth wave

Phase 2 was intentionally a single-worker phase because the entire delivery was inside `apps/web/src/components/copilot/` and `apps/web/src/lib/ai/tools/` — no way to split cleanly across three workers without merge conflicts on the render-pipeline wiring. One worker + clean commit hit prod inside 2 hours of v0.5.3. Memoed: parallelism is for disjoint file zones. When the entire delivery is one integrated surface, single-worker is faster than orchestration overhead.

### 6. Writing a migration is not deploying it (the v0.5.3 latent-500 incident)

Discovered mid-v0.5.4 release CI: `paywall-gate.spec.ts` was red on a `toHaveValue('')` for the Settings email field. First hypothesis was a stale race (widened the timeout — still failed). Real diagnosis by direct REST query: `profiles.timezone` column literally does not exist in prod. Migration 024 (added by worker P1 in the v0.5.3 wave) was committed to `supabase/migrations/` but never applied via `scripts/apply-migration-<N>.py` or an equivalent psql session. Same for migration 025 (`copilot_tool_calls.idempotency_key`).

The bug hid for ~4 hours (v0.5.3 tag → v0.5.4 tag) because `apps/web/src/app/api/profile/route.ts` returns 500 when the SELECT hits an unknown column, and the client's `useEffect` at `settings/page.tsx:204-230` catches ALL errors and just flips `profileLoaded=true` with an empty email string. Users saw an empty Settings page, not an error banner. No Sentry alert fires when the client swallows silently.

Applied 024 + 025 mid-flight (idempotent `if not exists`, ~10 seconds of psql). CI turned green immediately.

**Memoed:** every worker brief that touches `supabase/migrations/` must have a distinct step reading "apply this migration to prod via `python3 scripts/apply-migration-<N>.py` (or equivalent) and verify with a REST-API SELECT against the new column/index." The `if not exists` guards protect against re-runs; they do NOT protect against zero-runs. Also filed as a candidate CI safety check for v0.5.5: introspect `pg_class` + `information_schema.columns` in prod against every migration in the tree and fail the release step if any migration hasn't landed.

## Metrics to watch (next few days)

- `tool_audit_log` — count of `render_*` calls vs prose responses to quantitative queries. Baseline hypothesis: within a week, ≥60% of assistant answers containing a number are rendered, not prosed.
- Copilot chat message length distribution — expect a right-shift toward SHORT text + rich payload (as opposed to today's long markdown tables).
- User retention on the assistant tab — the render surface should feel more like a tool and less like a chatbot. Watch for a lift in return sessions per week.
- `/dev/pixel-ui` traffic — sanity check nobody is stumbling into it accidentally. If traffic is zero after a week, safe to leave; if non-zero, gate behind auth or move under `/app/dev/`.
- `PixelUI` component load errors — if any render_* payload with an unknown `kind` shows up in Sentry, we have a version drift between client and server tool registration. First-week alarm.
